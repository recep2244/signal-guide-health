Plan 01 specified FitbitProvider.syncHealthData() returns SyncResult with counts. So persistence must happen in syncFromProvider(). The mapping is:
- SyncResult.recordsCount.heartRate > 0 → call recordReading for HEART_RATE
- But SyncResult doesn't carry the actual values — only counts.

This is a design gap. Resolution: FitbitProvider.syncHealthData() should ALSO return the actual data, not just counts. Add an optional `readings` array to SyncResult OR have syncHealthData call recordReading() directly by accepting wearableService as a parameter OR change the approach.

**Recommended resolution (cleanest):** Have `syncHealthData()` in Fitbit and Withings providers call `wearableService.recordReading()` directly. Import wearableService lazily to avoid circular dependency: `import { wearableService } from '../wearableService'`. This means syncHealthData both fetches AND persists. The SyncResult counts reflect what was persisted.

```typescript
syncHealthData(accessToken, since, onReading?: (r: WearableReading) => Promise<void>)
```
And in syncFromProvider, pass `wearableService.recordReading.bind(wearableService)` as the callback.

Pick whichever approach avoids circular imports. Check the import chain: `wearableService.ts` does NOT import from `wearables/` directly (it imports from `alertService` and `prisma`).       await prisma.wearableDevice.update({
        where: { id: wearableId },
        data: { lastSyncAt: new Date() },
      });

      return { synced: totalSynced };
    },

    In the `if (isOAuthProvider(providerType))` branch, after getting the `authUrl`:
    - For Fitbit specifically, the authorization URL includes a code_challenge. The code_verifier must be stored in Redis.
    - The FitbitProvider (from Plan 01) has a `getCodeVerifier(state: string): string | undefined` method.
    - After calling `provider.getAuthorizationUrl(state)`, retrieve the verifier:
    ```typescript
    if (providerType === 'fitbit') {
      const fitbitProv = provider as any;
      const codeVerifier = typeof fitbitProv.getCodeVerifier === 'function'
        ? fitbitProv.getCodeVerifier(state)
        : undefined;
      if (codeVerifier && redis) {
        await redis.set(`pkce:${state}`, codeVerifier, 'EX', 600); // 10-minute TTL
      } else if (codeVerifier) {
        // Redis not available — fallback in-memory (single instance dev only)
        // Log warning
        console.warn('[OAuth] Redis unavailable — PKCE verifier stored in memory only');
      }
    }
    ```

    **Step B — Update `POST /callback/:provider` route:**
    For Fitbit, retrieve the code_verifier from Redis before calling `exchangeCodeForTokens`:
    ```typescript
    // Before: const result = await provider.exchangeCodeForTokens(code);
    // After (Fitbit-specific):
    let codeVerifier: string | undefined;
    if (providerType === 'fitbit') {
      if (redis) {
        codeVerifier = (await redis.get(`pkce:${state}`)) || undefined;
        await redis.del(`pkce:${state}`); // Single use
      }
      // Fall back to in-memory verifier from provider
      const fitbitProv = provider as any;
      if (!codeVerifier && typeof fitbitProv.getCodeVerifier === 'function') {
        codeVerifier = fitbitProv.getCodeVerifier(state);
      }
    }

    // Call exchangeCodeForTokens — for Fitbit, pass verifier via the provider's method
    // FitbitProvider.exchangeCodeForTokens accepts code but needs verifier
    // The provider stores it internally in pendingVerifiers Map keyed by state
    // For cleanliness, call the Fitbit-specific method if available:
    let result: WearableAuthResult;
    if (providerType === 'fitbit' && codeVerifier) {
      const fitbitProv = provider as any;
      result = typeof fitbitProv.exchangeCodeForTokensWithVerifier === 'function'
        ? await fitbitProv.exchangeCodeForTokensWithVerifier(code, codeVerifier)
        : await provider.exchangeCodeForTokens(code);
    } else {
      result = await provider.exchangeCodeForTokens(code);
    }
    ```

    **Note on Withings callback:** Withings `exchangeCodeForTokens(code)` needs no verifier — it works with the standard WearableProviderInterface signature. No callback changes needed for Withings.

    **Note on Garmin callback:** Garmin OAuth 1.0a uses an oauth_verifier passed as the `code` parameter. The existing `exchangeCodeForTokens(code)` on GarminProvider handles this correctly. No special treatment needed.
